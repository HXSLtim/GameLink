## ADR-001: 选择 Go + Gin 作为后端框架

### 状态
**已接受** - 2025-11-15

### 上下文
GameLink 是一个需要处理高并发请求的实时平台，需要：
- 高性能和低延迟
- 优秀的并发处理能力
- 快速的编译和部署
- 强大的类型系统

### 决策
选择 **Go 1.24** 作为后端语言，**Gin** 作为 Web 框架。

### 理由

| 优势 | 说明 |
|------|------|
| **性能** | Go 编译为机器码，性能接近 C/C++ |
| **并发** | Goroutine 和 Channel 使得并发编程简单 |
| **部署** | 单个可执行文件，无依赖 |
| **类型** | 静态类型，编译时发现错误 |
| **生态** | 丰富的库，Gin 是最流行的框架 |

### 负面影响
- 学习曲线比 Python/Node.js 陡峭
- 反射和泛型使用不当可能影响性能
- 比 Java 更少的"企业级"功能

### 替代方案

#### 方案 A: Node.js + Express
- ✅ 开发速度快，前后端统一语言
- ❌ 单线程模型，CPU 密集任务性能差
- ❌ 动态类型，运行时错误多

#### 方案 B: Java + Spring Boot
- ✅ 企业级功能丰富
- ❌ 启动慢，内存占用高
- ❌ 代码啰嗦

#### 方案 C: Python + FastAPI
- ✅ 开发速度快
- ❌ 性能不如 Go
- ❌ GIL 限制并发

### 结果
Go + Gin 提供了最佳的性能与开发效率平衡。

## ADR-002: 选择 React 19 + Ant Design 6

### 状态
**已接受** - 2025-11-15

### 上下文
管理后台需要：
- 丰富的 UI 组件
- 良好的开发体验
- 强大的生态系统
- 长期维护支持

### 决策
选择 **React 19** + **Ant Design 6** + **TypeScript**。

### 理由

| 优势 | 说明 |
|------|------|
| **组件丰富** | Ant Design 提供企业级 UI 组件 |
| **类型安全** | TypeScript 提供完整类型定义 |
| **生态成熟** | React 生态最成熟 |
| **长期支持** | Ant Design 由蚂蚁金服维护 |

### 负面影响
- 打包体积较大（Ant Design）
- 学习曲线较陡（React Hooks）

### 替代方案

#### 方案 A: Vue 3 + Element Plus
- ✅ 性能更好，打包更小
- ❌ 生态不如 React
- ❌ 团队不熟悉

#### 方案 B: Angular + Angular Material
- ✅ 框架完整，TypeScript 原生支持
- ❌ 学习曲线太陡
- ❌ 不够灵活

#### 方案 C: Next.js + shadcn/ui
- ✅ 现代化，开发体验好
- ❌ SSR 对管理后台无必要
- ❌ 团队无经验

### 结果
React 19 + Ant Design 6 是管理后台的最佳选择。

## ADR-003: 选择 WebSocket 而非 SSE

### 状态
**已接受** - 2025-11-20

### 上下文
系统需要实时推送：
- 系统状态更新
- 在线用户数
- 订单队列状态
- 聊天消息
- 告警通知

### 决策
使用 **WebSocket** (Gorilla WebSocket) 实现实时通讯。

### 理由

| 特性 | WebSocket | SSE |
|------|-----------|-----|
| **双向通讯** | ✅ 支持 | ❌ 仅服务端推送 |
| **二进制数据** | ✅ 原生支持 | ❌ 需要编码 |
| **浏览器支持** | ✅ 广泛支持 | ⚠️ 部分浏览器不支持 |
| **重连机制** | ✅ 容易实现 | ⚠️ 需要手动处理 |
| **服务器负载** | ⚠️ 维持长连接 | ✅ HTTP 标准 |

### 负面影响
- 需要处理连接状态和重连
- 防火墙可能阻止 WebSocket
- 需要实现心跳机制

### 替代方案

#### 方案 A: Server-Sent Events (SSE)
- ✅ 实现简单，自动重连
- ❌ 仅单向推送
- ❌ 不支持二进制数据

#### 方案 B: 轮询
- ✅ 实现最简单
- ❌ 延迟高
- ❌ 服务器负载高

#### 方案 C: Socket.IO
- ✅ 自动降级到轮询
- ❌ 需要额外依赖
- ❌ 协议开销大

### 结果
WebSocket 提供了最佳的性能和灵活性。

## ADR-004: 采用 AES-256-CBC 加密

### 状态
**已接受** - 2025-11-25

### 上下文
生产环境需要：
- 保护敏感数据传输
- 防止中间人攻击
- 符合安全合规要求

### 决策
采用 **AES-256-CBC** 加密请求体，生产环境必须启用。

### 理由

| 特性 | AES-256-CBC |
|------|-------------|
| **安全级别** | ✅ 军用级加密 |
| **性能** | ✅ 硬件加速 |
| **兼容性** | ✅ 广泛支持 |
| **标准** | ✅ NIST 认证 |

### 负面影响
- 增加 CPU 开销（约 5-10%）
- 需要管理密钥和 IV
- 调试困难（请求体加密）

### 替代方案

#### 方案 A: AES-256-GCM
- ✅ 认证加密，更安全
- ❌ 性能略低
- ❌ 兼容性稍差

#### 方案 B: 仅 HTTPS
- ✅ 无需额外实现
- ❌ 无法防御应用层攻击
- ❌ 日志可能泄露敏感信息

### 结果
AES-256-CBC + SHA-256 签名提供了良好的安全与性能平衡。

## ADR-005: 使用 PostgreSQL 覆盖索引

### 状态
**已接受** - 2025-12-01

### 上下文
系统需要：
- 快速的列表查询（分页）
- 高效的排序和筛选
- 最少磁盘 I/O

### 决策
使用 **PostgreSQL 覆盖索引** 优化查询性能。

### 理由

```sql
-- 覆盖索引示例
CREATE INDEX idx_orders_user_status_covering
ON orders (user_id, status, created_at DESC)
INCLUDE (id, total_price_cents);

-- 查询可以直接从索引获取数据，无需回表
SELECT id, total_price_cents
FROM orders
WHERE user_id = 1 AND status = 'pending'
ORDER BY created_at DESC;
```

| 优势 | 说明 |
|------|------|
| **减少 I/O** | 无需回表查询 |
| **加速排序** | 索引已排序 |
| **节省内存** | 只读索引，不读数据行 |

### 负面影响
- 索引占用更多空间
- 写入性能下降（约 10%）
- 需要定期 VACUUM

### 替代方案

#### 方案 A: 仅 B-Tree 索引
- ✅ 写入更快
- ❌ 查询需要回表

#### 方案 A: Redis 缓存
- ✅ 查询最快
- ❌ 数据不一致风险
- ❌ 成本更高

### 结果
覆盖索引在写入不多、查询频繁的场景下效果显著。

## ADR-006: 采用 Google Wire 依赖注入

### 状态
**已接受** - 2026-01-15 (Phase 4 架构改进)

### 上下文
代码组织需要：
- 清晰的依赖关系
- 易于测试
- 避免循环依赖

### 决策
采用 **Google Wire** 进行编译时依赖注入。

### 理由

```go
// wire.go
//go:build wireinject
// +build wireinject

func InitializeApp(db *gorm.DB, redis *redis.Client) *App {
    wire.Build(
        NewApp,
        NewHandler,
        NewService,
        NewRepository,
    )
}
```

| 优势 | 说明 |
|------|------|
| **编译时安全** | 编译时检查依赖 |
| **零运行时开销** | 代码生成，无反射 |
| **类型安全** | 编译时类型检查 |
| **易于测试** | 轻松 Mock 依赖 |

### 负面影响
- 需要代码生成步骤
- 学习曲线
- 初期设置复杂

### 替代方案

#### 方案 A: 手动依赖注入
- ✅ 简单直接
- ❌ 容易出错
- ❌ 代码重复

#### 方案 B: Dig (Uber)
- ✅ 运行时 DI
- ❌ 性能开销
- ❌ 错误在运行时发现

### 结果
Wire 提供了最佳的性能和安全性。

## ADR-007: 前端状态管理选择 Zustand

### 状态
**已接受** - 2025-11-18

### 上下文
管理后台需要：
- 简单的状态管理
- 良好的 TypeScript 支持
- 最少的样板代码

### 决策
选择 **Zustand** 而非 Redux。

### 理由

```typescript
// Zustand 示例
interface UserStore {
  users: User[];
  fetchUsers: () => Promise<void>;
}

export const useUserStore = create<UserStore>((set) => ({
  users: [],
  fetchUsers: async () => {
    const users = await api.getUsers();
    set({ users });
  },
}));
```

| 特性 | Zustand | Redux |
|------|---------|--------|
| **样板代码** | ✅ 最少 | ❌ 很多 |
| **TypeScript** | ✅ 原生支持 | ⚠️ 需要配置 |
| **学习曲线** | ✅ 平缓 | ❌ 陡峭 |
| **包大小** | ✅ 1KB | ❌ 3KB+ |
| **DevTools** | ✅ 支持 | ✅ 完善 |

### 负面影响
- DevTools 不如 Redux 完善
- 社区规模较小

### 替代方案

#### 方案 A: Redux Toolkit
- ✅ 成熟稳定
- ❌ 样板代码多
- ❌ 学习曲线陡

#### 方案 B: Jotai
- ✅ 更简单
- ❌ 团队无经验
- ❌ 生态较小

### 结果
Zustand 在简单性和性能之间取得了最佳平衡。

## ADR 提交流程

### 如何提交新的 ADR

1. **复制模板**
   ```bash
   cp docs/ADR/000-record-architecture-decisions.md docs/ADR/XXX-decision-title.md
   ```

2. **填写内容**
   - 状态设为 "待接受"
   - 完整填写上下文、决策、后果

3. **创建讨论**
   - 在团队群发起讨论
   - 或创建 GitHub Discussion

4. **决策确认**
   - 团队达成一致
   - 更新状态为 "已接受"
   - 合并到主分支

5. **实施决策**
   - 按照决策进行开发
   - 更新相关文档
