# GameLink 前端规划评审与优化建议（2026-02-12）

## 1. 结论

当前“15 个核心页面 + 业务链路”规划总体合理，符合 GameLink 当前项目形态。  
主要问题不在页面数量，而在**接口命名规范与实现契约不一致**，会导致联调成本持续上升。

## 2. 现状核对

### 2.1 页面覆盖

规划中的核心页面在 `app/src/pages` 基本都已存在并已注册，包含：
- 首页、陪玩师列表/详情、订单列表/详情/创建、消息列表/聊天室、钱包/充值、我的、公共频道、登录。
- 陪玩师侧页面（工作台、认证、服务管理）也已落地。

### 2.2 关键差异

1. **接口前缀风格混用**  
   当前前端同时存在 `/public`、`/user`、`/users`、`/player` 四种前缀，规划中写法更偏抽象（如 `/orders`、`/players`）。

2. **同一业务 HTTP 方法不统一**  
   例如订单取消/完成在当前实现中使用 `PUT`，规划表中部分写为 `POST`。

3. **陪玩师排班链路缺口**  
   工作台有“排班设置”入口，但之前缺少页面，形成跳转死链。

## 3. 优化后执行顺序（建议）

### P0（先做，避免联调反复）
- 统一“后端真实契约”为唯一数据源：路径、方法、字段名。
- 输出 API 映射表：`规划接口 -> 实际接口 -> 前端调用文件`。
- 固化命名规则（建议：公开接口 `/public/*`，用户态 `/user/*`，管理/陪玩师 `/player/*`）。

### P1（并行推进）
- 按业务链路验收，而非按页面验收：  
  登录 -> 浏览 -> 下单 -> 支付 -> 评价 -> 钱包流水。
- 每条链路定义最小可用验收标准（状态流转、金额一致性、未读数一致性）。

### P2（质量强化）
- 对 `api/*` 增加契约测试（最少 smoke 级）。
- 对关键 composable 增加单测（订单、聊天、钱包）。

## 4. 已实装优化

本次已补齐“排班设置”闭环：

- 新增排班 composable：`app/src/composables/usePlayerSchedule.ts`
  - 支持加载/保存排班
  - 默认 7 天排班模板
  - 支持每日可用开关与起止时间编辑

- 新增排班页面：`app/src/pages/player/schedule/index.vue`
  - 工作设置（自动下线、时区）
  - 每周排班编辑
  - 保存排班

- 新增页面注册：`app/src/pages.json`
  - `pages/player/schedule/index`

这项改动修复了工作台快捷入口死链，同时把 `player/schedule` 接口链路纳入可用状态。

## 5. 下一步建议

优先再落两件事：
1. 输出 `FRONTEND_API_MAPPING.md`（自动或半自动）；
2. 对“下单-支付-钱包流水”链路做一次完整联调记录（请求/响应样例 + 状态机）。
